Самая простая схема деплоя: сервер сам забирает исходники из GitHub, собирает образ и запускает
контейнер. Хватает ключа на чтение репозитория, git и Docker — без реестра образов и CI.

Подходит для одного сервера и небольшого проекта. Цена простоты: сборка идёт на самом сервере и упирается в его
процессор и память, а исходники лежат на сервере целиком.

## Deploy key

Deploy key — SSH-ключ одного репозитория с правом только на чтение. Если ключ утечёт, утекут лишь исходники
этого проекта. Действует, пока его не удалят из настроек репозитория. Ключ подключается к одному репозиторию,
поэтому второму проекту на том же сервере нужен свой.

## 1. Ключ на сервере

```sh
ssh-keygen -t ed25519 -f ~/.ssh/app_deploy -N '' -C 'app deploy'
cat ~/.ssh/app_deploy.pub
```

`-N ''` — ключ без пароля: так обновление работает без вопросов. Закрытый ключ `~/.ssh/app_deploy` остаётся на
сервере, открытый `app_deploy.pub` — в настройки репозитория.

## 2. Ключ в репозиторий

Репозиторий на GitHub → Settings → **Deploy keys** → Add deploy key: название, открытый ключ целиком,
**Allow write access** — пусто.

## 3. Клон на сервере

Своё имя хоста в `~/.ssh/config` указывает SSH, каким ключом ходить к этому репозиторию:

```
Host github-app
  HostName github.com
  User git
  IdentityFile ~/.ssh/app_deploy
  IdentitiesOnly yes
```

```sh
git clone git@github-app:example/app.git /srv/app
```

Второй проект — свой блок со своим ключом.

При первом подключении SSH покажет отпечаток ключа сервера — сверить с опубликованным в документации
GitHub и ответить `yes`. Дальше git ходит в репозиторий без вопросов.

Если в сети сервера порт 22 закрыт, SSH ходит к GitHub через 443: `HostName ssh.github.com` и `Port 443`.

## 4. Настройки и Compose

Настройки сервера лежат рядом с клоном, вне репозитория: обновление их сохраняет, а в git они не попадают.

`/srv/app.env`:

```sh
APP_URL=https://app.example.com
DATABASE_URL=postgres://app:<пароль>@db:5432/app
```

`compose.yaml` в репозитории:

```yaml
services:
  app:
    build: .
    env_file: ../app.env
    ports:
      - '127.0.0.1:3000:3000'
    restart: unless-stopped
    healthcheck:
      test: ['CMD', 'wget', '-qO-', 'http://127.0.0.1:3000/_health']
      interval: 30s
      timeout: 5s
      retries: 3
```

- `127.0.0.1:3000` — приложение доступно только с самого сервера; снаружи к нему ходит прокси (nginx, Caddy).
- `restart: unless-stopped` — контейнер поднимается после перезагрузки сервера.
- `healthcheck` — Docker сам проверяет, что приложение отвечает. Команда зависит от образа: `wget` есть в Alpine,
  в других образах — `curl` или своя проверка.

## 5. Первый запуск

```sh
cd /srv/app
docker compose up -d --build
```

`--build` собирает образ из исходников, `-d` запускает контейнер в фоне.

## 6. Проверка

```sh
docker compose ps
```

```
NAME        IMAGE     SERVICE   STATUS                    PORTS
app-app-1   app-app   app       Up 2 minutes (healthy)    127.0.0.1:3000->3000/tcp
```

- **Up … (healthy)** — контейнер работает и отвечает на проверку здоровья;
- **(health: starting)** — проверка ещё идёт, подождать `interval`;
- **(unhealthy)** или **Restarting** — смотреть логи.

```sh
docker compose logs -f --tail=100 app
curl -s http://127.0.0.1:3000/_health
```

`docker ps` показывает то же по всем контейнерам сервера.

## 7. Обновление

Сначала забрать изменения — одним из двух способов:

**Осторожно — `git pull --ff-only`**

```sh
cd /srv/app
git pull --ff-only
```

Принимает только новые коммиты поверх текущих. Если история разошлась — кто-то закоммитил прямо на сервере или
в репозиторий запушили с `--force`, — pull останавливается с ошибкой `Not possible to fast-forward`, и сервер
остаётся на прежней версии. Дальше разбираться руками: `git status` и `git log` покажут, что не так.

Подходит, когда важно заметить любое расхождение.

**Всегда как в репозитории — `git reset --hard`**

```sh
cd /srv/app
git fetch origin
git reset --hard origin/main
```

Ставит клон ровно туда, где ветка стоит в репозитории, в том числе после `push --force`. Правки, сделанные руками
в файлах клона, стираются. Настройки в `/srv/app.env` лежат вне клона и остаются на месте.

Подходит, когда сервер — только копия репозитория и деплой должен проходить без участия человека.

Потом — сборка и запуск, одинаково для обоих способов:

```sh
docker compose up -d --build
docker compose ps
docker image prune -f
```

- `up -d --build` сначала собирает новый образ, потом пересоздаёт контейнер. Старый работает, пока идёт сборка;
  простой — только на перезапуск.
- `image prune` убирает старые образы, которые остались без имени после сборки.

Удобно сложить это в `deploy.sh` в репозитории и обновлять одной командой.

## Версии и откат

Чтобы деплоить версии, а не всё подряд из ветки, — переключаться на тег:

```sh
git fetch --tags --force
git checkout --force v1.4.0
docker compose up -d --build
```

`--force` у `fetch` подтягивает тег, даже если его перенесли на другой коммит.

Откат — то же самое с предыдущим тегом. Миграции базы при этом остаются применёнными, поэтому перед деплоем
с миграциями — резервная копия базы.

## Ресурсы сервера

Сборка — самая тяжёлая часть схемы: установка зависимостей и сборка фронтенда легко занимают 1–2 ГБ памяти.
На дешёвом сервере с 1 ГБ это может переполнить оперативку: система начнёт убивать процессы, и под удар попадёт
уже работающее приложение или база.

- **Файл подкачки** на 1–2 ГБ даёт сборке запас: она идёт медленнее, зато доходит до конца.
  ```sh
  sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile
  sudo mkswap /swapfile && sudo swapon /swapfile
  echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
  ```
- **Деплой в тихое время** — пока идёт сборка, сервер отвечает медленнее.
- **Свободное место**: образы и кэш сборки копятся, `docker system df` показывает, сколько занято.

Если сборка регулярно упирается в память — пора собирать образ в другом месте (раздел ниже).

## Смена ключа

Сервер переехал или ключ мог утечь — завести новый ключ тем же способом, добавить в
репозиторий, поменять `IdentityFile` и удалить старый ключ в настройках репозитория. С этого момента старый ключ
перестаёт открывать репозиторий.

## Когда схемы станет мало

Следующий шаг — собирать образ в CI и класть в реестр (GitHub Container Registry), а на
сервере делать `docker compose pull` и `up -d`. Сервер тогда освобождается от сборки и исходников, а один и тот
же образ можно проверить и задеплоить на несколько серверов.
